## 1. curl --data-urlencode 二次编码与空格口径（164）

- **复核失败点原文**：`--data-urlencode 'a%20b=c d'` 中 `a%20b` 被再次 URL 编码成 `a%2520b`；且空格输出 `%20` 而非 curl 实际的 `+`。
- **根因**：`urlEncodeData` 对 name 与 value 一起做 RFC3986 编码；curl 语义是「name 已编码、原样使用，只编码 value」，且按表单编码把空格写成 `+`。
- **修复位点**：`tools/it/curl-parser.html` 的 `urlEncodeData` 只编码 `=` 右侧 value，空格经 `%20 → +`；裸值整体编码。
- **验证证据**：`CURLENC` 断言输出含 `a%20b=c+d` 且无 `a%2520b`；既有 `q=a b` 用例期望同步改为 `q=a+b`。
- **判别力实测**：恢复连 name 一起编码后出现 `a%2520b`；仅把空格改回 `%20` 时 `q=a+b` 用例转红。

## 2. shell 续行被折叠成空格（166）

- **复核失败点原文**：`curl https://exa\` + 换行 + `mple.com` 被全局替换成 `https://exa mple.com`，URL 只取到 `https://exa`；单引号内的反斜杠/换行也被错误折叠。
- **修复位点**：`parse()` 新增 `joinContinuations` 按引号上下文扫描：未引用/双引号内删除「`\` + 换行」二者（词中续行直接拼接），单引号内保留字面反斜杠与换行，双引号内其他 `\x` 转义原样保留。
- **验证证据**：`CURLJOIN` 断言 URL 为 `https://example.com`；既有「URL 在下一行」用例仍通过（续行后的空格保留）。
- **判别力实测**：恢复全局替换为空格后 URL 变 `https://exa` ⇒ 转红。

## 3. 签名页 & 未全量转义（185）

- **复核失败点原文**：`escHtml` 只转义「带分号实体」前的 `&`；浏览器仍会解析无分号实体（`&copy` → ©），待签名串的显示值与实际参与签名的字节不一致。
- **修复位点**：`tools/it/api-sign-generator.html` 的 `escHtml` 改为所有 `&` 一律转义，再处理 `<>"'`。
- **验证证据**：`SIGNENT` 断言 `&copy`/`&#169;` 均变 `&amp;…`、`<b>` 仍转义、无裸 `&copy`；既有 XSS 用例期望同步为 `=1&amp;secret=s`。
- **判别力实测**：恢复旧条件后 `&copy` 保留原样 ⇒ `SIGNENT` 转红。

## 4. Base32 标准模式放行缺填充（193）

- **复核失败点原文**：缺填充的 `MZXW6YQ` 在标准模式下仍被解出；RFC 4648 标准模式要求末组补齐。
- **修复位点**：`tools/it/base32-encode.html` 的 `base32ToBytes(str, allowUnpadded)`：`pad===0 && need>0` 且未允许时抛「缺少 Base32 填充」；新增解码侧复选框 `#allowNoPad`（默认关闭），勾选后按规则补回。FAQ 与 `content_deepdive.json`、英文映射同步。
- **验证证据**：`B32PAD` 断言严格模式 `MZXW6YQ:ERR`、`ME======:OK1`、`ME=======`/`MZXR`/`A` 均 ERR；允许模式 `ALLOW:4`。
- **判别力实测**：去掉缺填充分支后 `MZXW6YQ:OK4` ⇒ 转红。
