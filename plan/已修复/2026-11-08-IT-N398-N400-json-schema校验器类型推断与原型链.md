## 一、缺陷与修复

### IT-N398（高）schema 根省略 `type:"object"` 时 required/properties/additionalProperties 全被跳过
- 失败点：`walk` 只有在 `schema.type === 'object'` 时才进对象分支；真实 schema 里省略根 `type` 极常见（`properties`/`required` 本身就隐含对象约束），此时 `typeOK(undefined)` 返回 true、两个分支都不进 ⇒ **明显非法的数据被判「校验通过」**。
- 根因：把「类型声明」当成「分支开关」，而 JSON Schema 的约束关键字与应用条件是分离的。
- 修复位点：`walk` 先取 `typeList`（支持联合数组），再按关键字推断角色：
  ```js
  const hasObjKw = schema.properties !== undefined || schema.required !== undefined || schema.additionalProperties !== undefined;
  const hasArrKw = schema.items !== undefined;
  const explicitObj = typeList.indexOf('object') >= 0;
  const explicitArr = typeList.indexOf('array') >= 0;
  const asObject = explicitObj || (!typeList.length && hasObjKw);
  const asArray  = explicitArr  || (!typeList.length && !hasObjKw && hasArrKw);
  ```
  且只有**显式**声明 object/array 时才报「不是对象 / 不是数组」——未声明时对非对象实例保持「空过」（符合规范的空过语义，避免 `{"items":{…}}` 遇到字符串实例误报）。
- 证据：`{"required":["a"],"properties":{"a":{"type":"string"}}}` + `{"a":1}` → `类型不匹配 root.a: 期望 string`（修复前「校验通过」）；同 schema + `{}` → `缺少必填字段: root.a`；`{"properties":{…},"additionalProperties":false}` + `{"a":"x","b":1}` → `存在未允许字段: root.b`；`items` 内省略 type 的子 schema 也能校验到 `root[1].id`。

### IT-N400 `type` 联合数组永远通过；`in` 走原型链使 `toString`/`constructor` 绕过检查
- 失败点①：`typeOK` 用 `schemaType === 'string'` 之类逐字符串比较，`type:["string","number"]` 是数组 ⇒ 全部 false ⇒ 落到 `return true`，任意数据放行。
- 失败点②：required/properties/additionalProperties 用 `k in val` / `k in props`，`in` 会命中 `Object.prototype` ⇒ `required:["constructor"]` 对 `{}` 判通过，额外字段 `toString` 也漏报。
- 修复位点：`typeOK` 增加数组分支（任一匹配即通过，递归自身）；新增 `hasOwn(o,k) = o != null && Object.prototype.hasOwnProperty.call(o,k)`，三处成员判断全部替换；错误文案对联合类型输出 `string / number`。
- 证据：`{"type":["string","number"]}` + `{}` → `类型不匹配 root: 期望 string / number`；`{"type":"object","required":["constructor"]}` + `{}` → `缺少必填字段: root.constructor`；`{…,"additionalProperties":false}` + `{"a":"x","toString":1}` → `存在未允许字段: root.toString`。
