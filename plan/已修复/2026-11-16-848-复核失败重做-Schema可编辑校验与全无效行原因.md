## 1. Schema 验证缺少可编辑入口且合法性判定不完整（603）

- **复核失败点原文**：验证输出区当前可编辑或粘贴的 Schema；非空非法 JSON 报错；对合法 Schema 作合理结构校验。当前 `tools/it/json-schema-generator.html` 的 `#output` 是普通 `div`，没有 `contenteditable` 或输入控件；`validateSchema()` 在非空文本不含 `{` 时也会回退 `lastSchema`（`oops` 不作为非法 JSON 报错）；解析错误只 toast，未同步状态。`__schemaIssues()` 要求 required 每项必须列于同一层 properties，`{"type":"object","required":["a"]}` 与布尔 Schema 都被错误拒绝。
- **根因**：
  1. `#output` 只做高亮渲染，没有任何输入通道；
  2. `validateSchema` 以「文本里有没有 `{`」区分「空/占位」与「用户输入」，把 `oops` 这类非 JSON 文本当占位符静默回退 `lastSchema`；
  3. `required` 校验附加了 draft-07 并不存在的「必须出现在同层 properties」约束；`__schemaIssues` 入口把非对象一律判错，未放行布尔 Schema。
- **修复位点**：
  - `#output` 加 `contenteditable="true" spellcheck="false"`，并在上方补一行提示（`data-zh` 双语），说明输出区可编辑/粘贴、验证覆盖 draft-04/06/07 与 2020-12 通用结构、布尔 Schema 合法；
  - `validateSchema()` 改为：仅「空/占位」（`__schemaIsPlaceholder`）才回退 `lastSchema`，其余非空文本一律 `JSON.parse`；语法错误与结构错误分别写 `statusText`（`❌ Schema 无效：JSON 语法错误…` / `❌ Schema 结构错误：…`）并 toast；
  - `__schemaIssues()` 放行 `true/false`（任意层级子 Schema），删除「required 项须在同层 properties」的附加约束，仅保留「required 必须是字符串数组」；
  - 门禁 harness `scripts/verify_it_calc.js` 的 `getEl` 还原 HTML 的 `contenteditable` 属性（此前只还原 input 的 type/min/max/step，非表单容器的可编辑入口无法被断言）。
- **验证证据**：
  - 新增 `SCHEMAOK`（`{"type":"object","required":["a"]}` ⇒ `✅ Schema 结构有效`）、`SCHEMABOOL`（`true` ⇒ 有效）、`SCHEMATYPE`（`{"type":"objct"}` ⇒ `❌ Schema 结构错误：root.type: objct`）、`SCHEMAEDIT`（`#output` 的 `contenteditable==='true'`）；
  - 原 `SCHEMAVAL` 的 `required: ghost` 口径不成立（该 Schema 合法），改写为 `{"required":"a"}` ⇒ `root.required: not a string array`；
  - `SCHEMAJSON` 的注入文本由 `{oops` 改为 `oops`（旧代码对有 `{` 的文本本就会解析，只有无 `{` 的才走逃生分支），并同时断言 `statusText` 同步错误。
  - `node scripts/verify_it_calc.js json-schema-generator` ⇒ 11/11。
- **判别力实测**：
  - 布尔放行改回「非对象一律报错」⇒ `SCHEMABOOL` 转红；
  - 移除 `#output` 的 `contenteditable` ⇒ `SCHEMAEDIT` 转红；
  - 恢复「required 须在 properties 中」⇒ `SCHEMAOK` 转红；
  - 恢复 `raw.indexOf('{') < 0` 回退 ⇒ `oops` 被当占位符放行，`SCHEMAJSON` 转红（同一轮 `SCHEMAOK` 亦红，其余 9 条仍绿）。

## 2. 全部行无效时不列出具体原因（669）

- **复核失败点原文**：`tools/metalwork/analysis-35.html:213` 在没有有效行时提前返回，只显示「请输入至少一行」和无效行数；后面逐条输出原文和原因的 `skipped.forEach` 不会执行。例如仅输入 `short shot,-1,2`，看不到「次数须为正整数」和该行原文。
- **根因**：逐条原因列表写在「有有效行」的主渲染路径里，`!rows.length` 早退分支只拼了计数，未复用该列表。
- **修复位点**：抽出 `skipBox(skipped)`（空/无参返回空串，避免兜底阶段无参调用抛错），早退分支 `…+"</p>"+skipBox(skipped)`，主渲染路径改为 `h+=skipBox(skipped)`，两条路径共用同一渲染。
- **验证证据**：新增用例「全行无效」——`trials=6, data=short shot,-1,2`，探针读 `#res.innerHTML` 同时断言「（1 行无效）」「short shot,-1,2」「次数须为正整数」三项。`node scripts/verify_metalwork_calc.js analysis-35` ⇒ 5/5。
- **判别力实测**：撤掉早退分支的 `+skipBox(skipped)` 后探针输出 `A35ALL BAD:[ 请输入至少一行…（1 行无效） ]` 转红；恢复即绿。
- **附注**：该用例必须用单一探针串，不能拆成三条 `expect`——harness 的 `expect` 是「任一命中即通过」，拆开后「（1 行无效）」会先命中造成假通过（本轮已实测到这一假绿并改掉）。

## 3. GraphQL 自动补强用例可由输入回显通过（424）

- **复核失败点原文**：`scripts/verify_it_calc.js` 自动补强用例注入的 input 正是 `1\n2\n3`，而 `collectStrings()` 会把输入框 value 的空白折叠后加入断言文本，因此输入字段本身就产生「1 2 3」，无需格式化成功即可命中；该用例也无法验证 4 空格缩进。
- **根因**：断言锚落在「所有元素字符串拼接」上，锚串等于（折叠后的）输入值；且没有区分 2/4/Tab 缩进与压缩是否真的丢弃注释。
- **修复位点**：把该条自动用例替换为 3 条探针用例（`it/graphql-formatter`）：
  - `GQL424`：`query{a{b c}}` + `#indent=4` ⇒ 逐字符断言 `#output` 恰为 `query{ / ····a{ / ········b c····} / }`，并断言 `#err` 含「格式化成功」；
  - `GQL424I`：同一输入改 `#indent=2` ⇒ 恰为 2 空格缩进版，与 4 空格互为反向；
  - `GQL424M`：`query{# keep\n a b}` ⇒ 压缩恰为 `query{ a b}`（注释被丢弃、相邻 name 保留单空格），且输入回显仍含 `# keep`。
  - 三条用例的值都在 `clicks` 内写入 `#input`/`#indent`：该页脚本末尾 `loadSample()` 会重置输入，走 `inputs` 注入会被随后的 boot 覆盖（本轮已实测到该覆盖）。
- **验证证据**：`node scripts/verify_it_calc.js graphql-formatter json-schema-generator` ⇒ 15/15。
- **判别力实测**：把 `getIndent()` 固定返回 2 空格（等价「忽略 #indent」）⇒ `GQL424` 转红、`GQL424I` 仍绿，互为反向；恢复后 4/4。
