# 850 批：复核失败重做（价格弹性导出/建议、目标分解占比、LTV 空 CAC）· 申请再次复核

来源：`plan/复核失败/` 中 3 条（553、559、563）。

## 1. 价格弹性：导出未守卫、建议与数据相反、验收算例不符（553）

- **复核失败点原文**：`tools/marketing/price-elasticity.html` 的 `__peExport()` 只校验四项 > 0，P₁ = P₂ 时 dP = 0，导出会写入 `Infinity`/`NaN`；建议只按 |PED| 套话（如价格 100→110、销量 100→120 时 ped>0、收入 +32%，却提示「涨价会减少收入」）；原验收记录称 100→90、1000→1200 得 −2.478、收入 +17%，实际按中点法是 −1.727、+8%，−2.478 对应的是 q₂=1300。
- **根因**：导出与计算各写一套校验/公式；建议用弹性档位代替实际收入方向；验收数据取自页面默认 q₂（1300）却写成 1200。
- **修复位点**：
  - 抽出 `__peAdvice(ped, absPed, revChange, revPct, priceUp, en)`：先给 |PED| 档位，结论一律按本次 `revChange` 的实际符号写「增加/减少 X%」，ped>0 时追加同向变动提示；`calc()` 与 `__peExport()` 共用；
  - 导出加 `if(p2===p1)` 守卫，toast 提示「价格未变化（P₁ = P₂），需求价格弹性无定义」并返回，不再写表。
- **验证证据**：
  - 新增「纠正验收」用例：100→90、1000→1200 ⇒ 断言 `-1.727` 与 `8.0%`；
  - 新增「建议一致」用例：100→110、100→120 ⇒ 断言「本次提价后总收入增加 32.0%」；
  - 新增 `PE553E` 导出守卫用例：P₁ = P₂ = 100、Q₁ = 100、Q₂ = 120，探针要求 toast 含「价格未变化」且导出表无 `Infinity`/`NaN`。
  - `node scripts/verify_marketing_calc.js price-elasticity` ⇒ 5/5。
- **判别力实测**：把建议改回「|PED|>1 ⇒ 涨价会减少收入」⇒ 建议一致用例转红；删掉导出的 `p2===p1` 守卫 ⇒ `PE553E` 转红（导出表出现 Infinity）；恢复即绿。

## 2. 目标分解：图表校验不完整、导出占比与主表不一致（559）

- **复核失败点原文**：`tools/sales/target-breakdown.html` 的 `__tbExtras()` 只校验合计 > 0，负权重（如 −10/30）仍会画图；输入无效时直接 return 也不清除旧图。导出另用 `target/total` 重算占比，均分 1000/3 时主表为 33.4/33.3/33.3%、导出却是 33.3/33.3/33.3%，却仍写「合计 100.0%」。
- **根因**：图表校验与主表/导出校验不是同一套；占比尾差只在主表路径修正，导出绕过了 `computeAll`。
- **修复位点**：
  - 新增 `computeAll(total, mode, sumWeight)`，统一产出 `targets/pcts`（尾差归最大项），`calc()`、`__tbkExport()`、`__tbExtras()` 共用；
  - `__tbExtras()` 复用完整校验（总目标 > 0、至少一名成员、权重非负且合计 > 0），无效时 `clearRect` 清空上一轮画布；
  - 导出合计行改为实际 `pcts` 求和（修正后为 100.0%），不再硬编码。
- **验证证据**：
  - 新增 `TB559`：3 人权重 10/10/10、total=1000、avg 模式，导出后断言表内同时出现 `33.4%`、两个 `33.3%` 与合计 `100.0%`；
  - 新增 `TB559N`：权重 −10/30，替换 `TBKit.chart.bar` 为计数桩，断言调用 0 次且主表出现「权重不能为负数」。
  - `node scripts/verify_sales_calc.js target-breakdown` ⇒ 3/3。
- **判别力实测**：导出改回 `shares.map(t => t/total*100)` 后 `TB559` 转红（只剩三个 33.3%）；把图表校验退回「仅合计 > 0」后 `TB559N` 转红（chart.bar 被调用）；恢复即绿。

## 3. LTV：空 CAC 被当 0、生命周期重复、保存历史绕过校验（563）

- **复核失败点原文**：`tools/marketing/marketing-ltv-calculator.html` 详情模式用 `parseFloat(cac)||0`，清空 CAC 后按 0 通过校验并继续算 LTV；详细拆解表与相关指标卡重复展示「预期生命周期」；`saveHistory()` 另行 parseFloat 存入历史，空 CAC 时得到 `NaN`（JSON 序列化为 `null`）。
- **根因**：数值读取用 `||` 兜底，抹平了「空串」与「合法 0」；保存历史没有复用计算的校验结果。
- **修复位点**：
  - `cacRaw = String(value).trim()`，空串单独报「请填写 CAC（可为 0，但不可留空）」，0 仍合法；错误分支清空 `window.__ltvLast`；
  - `calc()` 校验通过后写入 `window.__ltvLast = {mode, inputs, ltv}`；`saveHistory()` 只接受该快照（并校验 mode/有限值/结果区无 `tip-error`），直接写入快照数值；
  - 删除详细拆解表中重复的「预期生命周期」行，仅保留相关指标卡。
- **验证证据**：
  - `LTV563`：清空 CAC ⇒ 结果区含「请填写 CAC」且不出现 `LTV:CAC`；
  - `LTV563D`：详情模式结果区「预期生命周期」出现次数恰为 1；
  - `LTV563S`：清空 CAC 后 `saveHistory()` 不新增历史条目；
  - 既有 detail 用例（LTV 600.00、LTV:CAC 3.00）保持不变。
  - `node scripts/verify_marketing_calc.js marketing-ltv-calculator` ⇒ 5/5。
- **判别力实测**：删掉空串专属提示（退回只判区间）⇒ `LTV563` 转红；把重复行加回拆解表 ⇒ `LTV563D` 转红；同时去掉 `__ltvLast` 清空与 saveHistory 的 `tip-error`/mode 校验 ⇒ `LTV563S` 转红；恢复即绿。
