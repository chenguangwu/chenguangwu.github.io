## 一、缺陷：MD5 按 UTF-16 码元填充，非 ASCII 摘要全错

`md5()` 内部的 `convertToWordArray(str)` 用 `const lMessageLength = str.length`（UTF-16 码元数）并逐码元 `str.charCodeAt(lByteCount)` 写入 32 位字；长度字 `lMessageLength << 3` / `>>> 29` 也随之按码元算。MD5（RFC 1321）的填充与长度字段单位是**字节**，必须先把文本按 UTF-8（RFC 3629）编码。同页 `utf8ToBytes()` / `sha()` 走 `TextEncoder` 本就正确，页面「输入编码」表也写明「同一文本须固定 UTF-8 编码」⇒ 同页 MD5 与 SHA 口径相反，中文用户拿到的 MD5 与 `md5sum`、后端、CI 全部对不上。

**复现**（`node` + `vm` 抽取页面真实内联 `md5()`，对照 `crypto.createHash('md5')`）：

## 二、修复

`convertToWordArray()` 只改三处，四轮函数与常数表逐字不动：

```js
function convertToWordArray(str) {
  /* IT-N469：MD5 填充以「字节」为单位（RFC 1321）… */
  const bytes = utf8ToBytes(str);
  let lWordCount;
  const lMessageLength = bytes.length;      // 旧：str.length
  …
  lWordArray[lWordCount] = (lWordArray[lWordCount] || 0) | (bytes[lByteCount] << lBytePosition); // 旧：str.charCodeAt(...)
  …
  lWordArray[lNumberOfWords - 2] = lMessageLength << 3;   // 自然按字节，无需改
  lWordArray[lNumberOfWords - 1] = lMessageLength >>> 29;
}
```

复用同页既有 `utf8ToBytes()`，不新造编码函数，保证 MD5/SHA 同口径。

**边界验证**（`vm` 直跑页面函数 vs Node crypto）：`a`/`中` 各重复 55/56/63/64/65/119/120/1000 次（覆盖 64 字节分组边界）、`测试`×10、`a`×55+中文、双 emoji、`é`、`\u0000`、`ß`、ZWJ 家庭 emoji（25 字节）、`upperCase` 大写开关 —— **全部一致，0 失败**。

### 公式说明与英文映射同步

`formula-eq` 末尾补：「输入先按 UTF-8（RFC 3629）编码为字节序列，填充长度按字节计（RFC 1321），与同页 SHA 同口径」。该整段中文是 `i18n/tools/en/it/calc-10.json` 的 **map key**，故同批删旧 key、写新 key（中文原文 422 字符）与对应英文译文。静态断言：HTML `.formula-eq` 的 `textContent` 与 map key **精确相等**，译文含 `UTF-8 encoded (RFC 3629)`，旧 key 残留 0。已确认 `i18n/tools/content_deepdive.json` / `scripts/apply_it.py` 等构建源无该串副本，不会被 `_build.py` 覆盖。
