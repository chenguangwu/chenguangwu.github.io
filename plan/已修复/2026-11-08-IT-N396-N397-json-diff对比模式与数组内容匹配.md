## 一、缺陷与修复

### IT-N396 「对比模式」下拉从未被读取，深度/简单两种模式输出完全相同
- 失败点：`<select id="diffMode">` 只有 `onchange="doDiff()"`，`doDiff` 内部从不读它，两种模式都跑 `deepDiff` + 同一套逐行 diff 与统计。
- 根因：控件只接了「触发重算」，没接「参与计算」。
- 修复位点：`doDiff` 开头读 `diffMode`，`simple` 走新增的 `simpleDiff(a,b)`——只遍历顶层键，嵌套结构视为一个值（`jdKey` 规范序列化比较），变化合并成一处 `mod`，不展开路径；`deep` 仍走 `deepDiff`。
- 证据（jsdom 实测，同一输入 `{"a":{"x":1},"b":2}` → `{"a":{"x":9},"b":2}`）：deep = `[{"op":"mod","path":"a.x","from":1,"to":9}]`；simple = `[{"op":"mod","path":"a","from":{"x":1},"to":{"x":9}}]`。数组 `{"t":[1,2]}` → `{"t":[1,2,3]}`：deep = `add t[2]`；simple = 一处 `mod t`。

### IT-N397 数组只按索引对齐，「按内容匹配」未实现，FAQ 还引用了不存在的开关
- 失败点：`deepDiff` 数组分支固定按 `i` 逐项比；说明区写「可按索引对齐，也可按内容做匹配」、FAQ 写「语义比较需开启键匹配模式」，但页面没有任何开关，也无内容匹配实现。
- 根因：承诺写在文案里，实现从未跟上。
- 修复位点：① 新增复选框 `#arrayMatch`（「数组按内容匹配」，默认不勾，与 FAQ「需开启」口径一致）；② 新增 `jdCanon`/`jdKey`（对象键排序后的规范序列化，键序不同也算同一元素）、`jdLcsPairs`（最长公共子序列配对，`n*m > 200000` 时返回 `null` 退回下标对齐，防 O(n·m) 卡页）；③ 数组分支在开启时先用 LCS 对齐相同元素，剩余元素按顺序两两递归（内容真变了的仍报路径级 `mod`），多出来的才报 `add`/`del`。
- 证据：`{"tags":["a","b"]}` → `{"tags":["b","a"]}` 纯换序 ⇒ 0 处差异（修复前 2 处 mod）；`{"tags":["a","b"]}` → `{"tags":["b","a","c"]}` ⇒ 仅 `add tags[2]`（修复前 2 mod + 1 add）；对象数组 `[{id:1},{id:2}]` 换序 ⇒ 0 处；`[{id:1,n:"a"}]` → `[{id:1,n:"b"}]` ⇒ 仍精确报 `mod items[0].n`（残余配对没丢精度）。
- 文案同步：说明区「数组」条目改为「默认按索引对齐；勾选「数组按内容匹配」后按元素内容对齐…」，FAQ 改为同一口径（不再出现不存在的「键匹配模式」），`formula-eq` 补两种模式与匹配算法。

### 同批顺带修：成员判断走原型链
- 失败点：`deepDiff` 的对象分支用 `!(k in b)` / `!(k in a)` 判成员，`in` 会命中 `Object.prototype` ⇒ 键名是 `constructor`/`toString` 等时被当成「两侧都有」，进而递归比对到一个函数，报成 `mod` 甚至把 `del` 吞掉。
- 修复位点：改为 `Object.prototype.hasOwnProperty.call(...)`（`simpleDiff` 同样处理）。
- 证据：左 `{"constructor":1}` 右 `{}` → 正确 `del constructor`（修复前报 `mod`）。

## 二、用例清理

原 `json-diff` 有一条自动补强的弱用例（expect 命中下拉框回显 `simple`，属零判别力），本批随页面改动一并换成真实行为断言：非法 JSON（`1\n2\n3`）必须只弹一次「JSON 解析错误」toast —— 与页面改动无关，但把它从「回显逃生」提升为「行为契约」。新增 7 条用例：deep 对照 1 条、simple 3 条、数组按内容匹配 3 条（含「换序+追加」四元组断言 `n=1 mod=0 add=1 p=tags[2]`），以及顺带修的原型链 1 条。
