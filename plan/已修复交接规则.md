# 已修复问题交接与复核规则

> 老板 2026-11-06 定，长期有效。修复方与复核方共同遵守，任一方改动本规则需同步 `plan/MASTER.md`、`plan/HANDOFF.md`、`DEV-PLAN.md`。

## 一、修复方（移交）

- 完成修改并通过门禁后，将记录从 `plan/categories/**` **移出**（移动，不是复制），移入 `plan/已修复/`。
- **一批一新文件**：命名 `YYYY-MM-DD-<NN-分类>-<主题>.md`（例 `2026-11-06-IT-N87-N92.md`），**只新建、不改旧**；不同批次不合并写同一文件，避免并行写入冲突。
- 每条须写明：原问题、修复内容与证据位点（文件:行号）、验证证据（Node 复算 / 门禁回归用例 / 官方向量）、门禁结论。
- **每批必须合并审计分支**：`git fetch origin audit/interaction-review` → `git merge origin/audit/interaction-review`，合并后优先处理 `plan/复核失败/` 中的条目。漏合并会导致复核结果长期不回流。

## 二、复核方（复核）

- 只复核 `plan/已修复/` 中已移交的记录，不重复复核未处理项。
- **复核通过 → 直接删除该记录**（已独立验证，不再留档）。
- **复核失败 → 写入 `plan/复核失败/<YYYY-MM-DD>-第N批.md`**，写明失败点、复现方式、涉及位点与待处理项；同时从 `plan/已修复/` 删除对应记录，等待修复方重做后重新移交。
- 复核结论必须区分「已修」与「仅部分修复」：只要原问题中有一项未落实，整条判失败，不能拆成通过。
- 部分修复、未处理的问题留在原分类清单；不能确认的专业问题移至相应待裁断清单，注明尚未确认，**不能当作通过或失败**。

## 三、目录生命周期

- 每个批次处理完后删除空的批次文件；`plan/已修复/` 仅存等待复核的批次，全部处理完时应为空。
- Git 不保留空目录，修复方新移交时重新创建即可。
- `plan/复核失败/` 的文件在对应条目重做并复核通过后一并删除。
