### LF-N7 工作日区间少算结束日，与公式、规则示例互相矛盾（高，确认源码缺陷）
- 描述：页面公式写「总天数 =（结束日期 − 开始日期）÷ 86400000 + 1（含首尾两天）」，规则区又写「周一到周五 = 5 个工作日」，但实现用 `while(d < end)` 逐日遍历，结束日整日不进循环；同日区间直接得到 0 天。
- 证据：`tools/life/workday-calculator.html:152`（+1 含首尾）、`:189`（周一至周五 = 5）、`:291-323`（`while(d < end)` 与 `totalDays++`）、`:325-326`（回显的结束日期为 1/31 当天）。node 按源码复算：2024-01-01→2024-01-05 输出 `totalDays=4, workDays=4, weekends=0`；2024-03-05→2024-03-05 输出 `totalDays=0, workDays=0`；2026-01-01→2026-01-31 输出 `totalDays=30`（含首尾应为 31）。
- 影响：`tools/life/workday-calculator.html`；所有工期/请假/交付窗口都少 1 天，且与页面自述的公式和示例冲突，同日查询得到 0 天。
- 方案：统一语义为「含首尾」时把循环改成 `while(d <= end)`，或把公式、示例改为「含起始不含结束」并同步结果文案；补充同日、周一至周五、跨月跨年用例。

### LF-N8 日期按 UTC 解析、星期按本地判断，非东八区用户整体错位一天（中，确认源码缺陷）
- 描述：`new Date('YYYY-MM-DD')` 按 UTC 午夜解析，随后 `getDay()`、`toLocaleDateString()` 按浏览器本地时区取值；UTC 以西时区会落到前一天，工作日/周末判定整体偏移，回显日期也早一天。
- 证据：`tools/life/workday-calculator.html:298-299`（UTC 解析）、`:311-314`（本地 `getDay()` + UTC 日期串）、`:325`（本地回显）。`TZ=America/Los_Angeles node` 复算：输入 2024-01-05→2024-01-08，开始日期回显 `2024/1/4`，遍历到的日期串仍是 01-05→01-07，且 `getDay()` 为 4/5/6（周四/五/六）；输入 2024-01-01→01-05（周一至周五）只计 `3` 个工作日。
- 影响：`tools/life/workday-calculator.html`；美洲/欧洲时区用户得到少一天且周末判断错位的工期，属跨时区可复现缺陷（中国时区下不可见）。
- 方案：统一用本地日期构造 `new Date(y, m-1, d)`（或全部走 UTC 并配 `getUTCDay()`/`toISOString()`），日期显示与判断保持同一时区口径；补跨时区快照用例。

### LF-N10 跨日停车把「每日封顶」当成整段封顶，长时间停车严重少算（高，确认源码缺陷）
- 描述：公式区写「每日封顶时按自然日分组取较小值后累加、跨日逐日分别计费」，实现只对整个停放时长算一次 `billable*rate` 再 `Math.min(fee, cap)`，跨多日仍只收一次封顶；同时免费时长也只扣一次。
- 证据：`tools/life/parking-fee.html:106`（按自然日分组）、`:170`（注意事项却改为「按连续小时估算」）、`:221-230`（`billable=Math.max(0,hours-free)`、`fee=Math.min(fee,cap)` 无按日拆分）。node 按源码复算：36h、10 元/h、免费 0、封顶 60 → `fee=60.00`（跨两日按页面口径应至少 60+60=120）；50h → `fee=60.00`（跨三日应约 180）；5.5h/免费1h/封顶60 → `45.00`（与示例一致）。

### LF-N18 万/亿分段把前导零当补位，默认输入即显示「〇一万二千三百四十五」（高，确认源码缺陷）

- 证据：`tools/life/chinese-number.html:154`（默认输入 `12345.67`）、`:273-292`（`padStart` + `zero` 标记 + `:284-287` 无条件补零）、`:265-269`/`:304-308`（段结果直接拼 `万/亿/万亿`）、`:377`（调用）。node 按源码复算：`12345.67` → 简体 `〇一万二千三百四十五`；`1000000` → `〇一百万`；`10001` → `〇一万〇一`；`1000000000000` → `〇一万亿`。
- 影响：`tools/life/chinese-number.html`；页面一打开（默认值）与「整数」「大额」预设均输出错误中文，所有 ≥1 万的金额大写（含人民币）同步带前导零，属高频可见错误。
- 方案：在段内增加 `started` 标记，只有已经输出过非零位时才补 `零`；段首补位零直接跳过。补 `10001`、`12345`、`1000000`、`100000001`、`1000000000000` 用例，并校验大写/人民币同步。

### LF-N19 小数部分被截断，0.999 直接输出「undefined角整」（高，确认源码缺陷）
- 描述：阿拉伯数字转简体/大写时统一用 `Math.floor(Math.abs(n))`，小数位完全丢弃；人民币大写用 `Math.round((abs(n)-intPart)*100)`，当舍入到 100 分时 `jiao=10`，而 `upperDigits[10]` 为 `undefined`。另有「元」与「分」之间缺 `零`、负数丢符号两处一致性问题。
- 证据：`tools/life/chinese-number.html:374-379`（`intPart` 截断后传给三个转换函数）、`:313-329`（`decPart` 可等于 100、`:321` 直接索引 `upperDigits[jiao]`）、`:512`（页面自带的「小数」预设 `0.5`）。node 按源码复算：`0.5` → 简体 `〇`、大写 `零`、人民币 `伍角整`；`0.999` → 人民币 `undefined角整`；`9.999` → `零玖元undefined角整`；`1.05` → `零壹元伍分`（应为「壹元零伍分」）；`-123` → 简体 `〇一百二十三`（丢负号）。
- 影响：`tools/life/chinese-number.html`；点击「小数」预设即得到与输入不符的中文，金额场景可能出现字面 `undefined`，用户会认为工具损坏。
- 方案：金额先量化到分，`decPart===100` 时向整数位进 1；简体/大写支持 `点` 后逐位读数；元与角分为零时补 `零`；负号统一前置。补 `0.5`、`1.05`、`0.999`、`-123`、`12345.67` 用例。

### LF-N20 罗马数字反查拆解式与结果互相矛盾，超范围提示错位（中，确认源码缺陷）
- 描述：`fromRoman` 的拆解式按字符逐个映射后用 `+` 连接，未处理减法组合；`XIV` 显示 `X=10 + I=1 + V=5`（合计 16）但结果 14，`MMXXIV` 显示合计 2026 而结果 2024。对超出 1–3999 的字符串（如 `MMMM`），回验路径把 `toRoman` 的字符串提示当作「正确写法」输出。正数输入还使用 `parseInt`，`1e3` 会被截成 1。
- 证据：`tools/life/roman-numeral.html:294-309`（`:297-303` 逐字符累加与减法处理、`:308` 拆解式生成）、`:282-292`（`toRoman` 超范围返回字符串）、`:306-307`（回验提示）、`:311`（`parseInt`）。node 按源码复算：`XIV` → `{result:14, break:'X=10 + I=1 + V=5'}`；`MMXXIV` → `{result:2024, break:'…合计 2026'}`；`MMMM` → `{result:'无效组合', break:'正确写法：超出范围 (1-3999)'}`；`parseInt('1e3')` → `1`（显示 `I`）。
- 影响：`tools/life/roman-numeral.html`；拆解式是页面主打的「可核对」内容，与结果对不上会直接削弱可信度；超范围输入给出自相矛盾的修正建议。
- 方案：拆解式按减法对（`IV=4`、`IX=9`、`XL=40`…）生成或改为纯符号展示；回验前先判 `total` 是否落在 1–3999；输入改用 `Number()` 并校验整数。补 `XIV`、`XLIX`、`MMMM`、`1e3` 用例。

### LF-N21 「23 人恰好超过 50%」文案与自定义总天数脱钩（低，确认源码缺陷）

### LF-N22 「体脂率估计」实为 BMI÷22×100，默认参数就显示 102%（高，确认源码缺陷）
- 描述：BMI 面板第四张统计卡标注「体脂率估计」，表达式却是 `BMI × 100 / 22`，量纲与含义都不是体脂率；默认 170 cm/65 kg 的 BMI 为 22.49，卡片直接显示 102%。

- 影响：`tools/life/daily-calorie-needs.html`；默认状态即出现生理上不可能的体脂率，用户会据此误判身材或直接不信任整页数据。

### LF-N23 BMI/BMR/TDEE 只用 falsy 校验，负身高、负体重、负年龄照常出结果（中，确认源码缺陷）
- 描述：三个面板的守卫均为 `if(!age || !height || !weight)`，负数与非有限值只要非 0 就通过；HTML 的 `min` 只约束步进按钮，脚本读取 `value` 时不受限。负身高会让 BMI 变负、负年龄会抬高 BMR，页面仍按正常结果展示。
- 证据：`tools/life/daily-calorie-needs.html:552`（BMI）、`:602`（BMR）、`:681`（TDEE）；输入框 `:205`/`:209`/`:213` 仅设 `min/max`。node 按源码复算：身高 `-170`、体重 `65` → BMI `-22.5`，状态「偏瘦」；年龄 `-5`、身高 `170`、体重 `65` 的男性 Mifflin BMR → `1742.5` 千卡。
- 影响：`tools/life/daily-calorie-needs.html`；手动输入负值（或粘贴带负号的体检数据）会得到看似正常的错误结论，且无任何提示。

### LF-N24 港码按「×3.14」线性换算，11 码得出负美码/负欧码（高，确认源码缺陷）
- 描述：港码被当作「周长 = 码数 × 3.14」的无截距直线，且反算直接除以 3.14；港码是带偏移的分级制（代码自己的注释也写「11号=50mm」），小码会换算出负的周长外推值，结果区仍照常打印负的美码/英码/欧码。`convert` 只校验基准周长 >0，不校验各制式换算结果。
- 证据：`tools/life/ring-size-converter.html:285-289`（`case 'hk': return v*3.14`）、`:294-304`（`circ/3.14`）、`:286`（注释「实际港码11号=50mm，则 1号=3.14mm」与实现矛盾）、`:319`（只判 `circ<=0`）、`:192`（页面示例「54mm → 17号」）。node 按源码复算：输入港码 `11` → 周长 `34.54 mm`，美码 `-0.62`、英码 `-0.66`、欧码 `-5.46`；输入港码 `1` → 美码 `-12.00`、欧码 `-36.86`。
- 影响：`tools/life/ring-size-converter.html`；港码是国内最常用口径，输入常见码数却得到负的海外码，按结果海淘必然买错。
- 方案：改用港码→周长的真实对照表（约 1 mm/码、带截距），或至少 `circ = a×码 + b` 且用同一组参数反算；对所有制式结果做 `>0` 校验并提示「该码数低于可换算范围」。补港码 1/11/17、周长 50/54/57 用例。

### LF-N25 欧码实现成「周长−40」（实为意码口径），55 mm 周长显示 EU 15（高，确认源码缺陷）
- 描述：页面把欧码定义为 `EU = 周长 − 40`，反算 `周长 = EU + 40`。ISO 8653 与主流对照表以「内周长 mm」作为欧码（54 mm 即 EU 54），`−40` 是意大利码口径。结果导致欧码输出整体小 40，输入欧码则周长被放大 40 mm。
- 证据：`tools/life/ring-size-converter.html:289`（`case 'eu': return v + 40`）、`:301`（`circ - 40`）、`:157`/`:195`（页面自述「欧码 = 周长 − 40；如 54mm → 14」）、`:175`（默认输入 55 mm）。node 按源码复算：默认 `55 mm` → 欧码 `15.00`、美码 `6.79`、英码 `7.21`、港码 `17.52`；输入欧码 `50` → 周长 `90.00 mm` → 美码 `19.47`、港码 `28.66`、直径 `28.65 mm`（美码 19.5 已超出常见戒指码上限）。
- 影响：`tools/life/ring-size-converter.html`；欧码是跨境选码的主要参考，现输出与任何欧洲商品标签都对不上，且会把正常欧码输入换算成畸形大码。

### LF-N26 罩杯下标整体偏移且 8 cm 处跳级，10 cm 差值得 D 杯（高，确认源码缺陷）
- 描述：`cupIdx = Math.round(diff/2.5) - 1` 再取 `cups[cupIdx+1]`，等于把 `cups` 数组整体右移两格：10 cm 差值本应 A 杯（源码注释亦写 `diff=10 -> A`），实际输出 D；12.5 cm 输出 E。另 `diff<8` 硬置 AA，`diff=8` 走公式得 C，7.9→AA、8.0→C 出现 AA→C 断崖。超大差值越过数组长度后输出 `?`。

### LF-N27 分钟取整未进位，42 g 双芯蜡烛显示「2小时60分钟」（中，确认源码缺陷）
- 描述：小时用 `Math.floor`、分钟用 `Math.round((burnHours-hours)*60)`，分钟可舍入到 60 而未向小时进位，直接拼成「N小时60分钟」；主结果又用 `toFixed(1)` 单独取整，与副行可能再差 0.1 小时。

### LF-N30 油耗分类声明 reciprocal 却按乘法换算，整类双向结果错位（高，确认缺陷）
- 描述：fuel 表中 km/L、mpg(US)、mpg(UK) 标了 `reciprocal: true`（与 L/100km 成反比），但 `convertFrom` 两个分支都只做 `val × fromFactor ÷ toFactor`，从未读取该标记。反比单位必须以 `factor ÷ value` 折算到基准，因此整类换算与同页速查文案、参考值全部矛盾；gal/100mi 属比例型，混在同一张表里更易掩盖问题。
- 证据：`tools/life/unit-converter.html:675-679`（reciprocal 声明与比例型混排）、`:682-684`（速查文案）、`:774-777`、`:790-793`（只用 factor 乘除）。
- 复现：8 L/100km → mpg(US) 实际 `0.034011`（期望 `29.40`）；10 L/100km → km/L 实际 `0.1`（期望 `10`）；1 mpg(US) → km/L 实际 `2.35215`（期望 `0.425`）；29.4 mpg(US) → L/100km 实际 `6915.32`（期望 `8.0`）。
- 影响：`tools/life/unit-converter.html`；油耗是换算器最常用分类之一，除「值为 1」的巧合外所有结果错 1–3 个数量级，速查项「8 L/100km ≈ 29.4 mpg」点下去得到 0.034。
- 方案：按单位语义分组——反比单位先算 `base = factor / value`，比例型保持 `value × factor`；输出端反比单位用 `factor / base`；补 8 L/100km ↔ 29.4 mpg、10 L/100km ↔ 10 km/L 往返用例。

- 证据：`tools/life/unit-converter.html:590`（dBm 声明）、`:771-777`（仅 temperature 特判）、`:799-800`（NaN → 空串）。

- 影响：`tools/life/unit-converter.html`；射频、音响场景常用 dBm，用户只能看到空结果，无法判断是输入错误还是工具不支持。

### LF-N32 能量速查引用不存在的 megajoule，点击抛 TypeError 且结果栏停留旧值（中，确认缺陷）

### LF-N34 清空任一温标输入框会被立即回填默认值，无法留空重输（中，确认缺陷）

- 复现：清空「华氏度」→ 该框立刻变回 `32.00`，摄氏度 `0.00`、开尔文 `273.15`（期望空值时不计算、保持空框并提示）。

### LF-N39 parseInt 静默截断非法字符，非法的「部分合法」输入照常出数（中，确认缺陷）
- 描述：四种前缀解析都用 `parseInt`，只有整串完全无法解析才会 `isNaN` 置「错误」；带非法尾巴或中间夹非法字符时会被截断后正常换算，与页面「解析失败时各栏置『错误』」的承诺不符。
- 证据：`tools/life/base-convert.html:309-321`（parseInt 与 isNaN 判定）。
- 复现：`0b1012` → 实际 dec `5`、bin `101`（期望「错误」，末位 2 不属于二进制）；`12a` → 实际 `12`；`0x1G` → 实际 `1`。
- 影响：`tools/life/base-convert.html`；用户粘贴带空格/注释的代码常量时会得到少一位的错误结果，且无任何警示。
- 方案：按前缀选定合法字符集后整串正则校验（`^[01]+$` 等），不匹配直接置「错误」；再用 `Number()`/显式逐位累加替代 `parseInt`。

### LF-N40 查询范围允许负数/0/小数，倒序区间照常渲染（低，确认缺陷）
- 描述：范围用 `parseInt(...) || 10`，负数、0、空值都被静默兜底或透传；负数会得到 `start > end` 的倒序区间，标题仍是「2024 - 2019 年附近的闰年：无」；0 被当成 10。年份同样走 parseInt，`2024.5` 静默按 2024。
- 证据：`tools/life/leap-year-checker.html:264-265`（parseInt 与 `||10`）、`:279-284`（start=y、end=y+range−1、for 循环）。

- 影响：`tools/life/leap-year-checker.html`；错误输入得到看似正常的空结果，用户会以为该区间真的没有闰年。
- 方案：年份与范围统一 `Number()` + `Number.isInteger` 校验（范围 1–500），非法时清空结果并字段级提示；标题改为「从 y 起 N 年」以匹配实现。

### LF-N41 练习计时用 setInterval 递减，后台标签页会明显走慢（中，确认缺陷）
- 描述：计时靠 `setInterval(...,1000)` 每次 `remaining--`，不读墙钟；后台标签页/系统休眠时定时器被节流，剩余秒数只按回调次数减少，5 分钟阶段可能走十几分钟，阶段切换与完成提示同步延后。
- 证据：`tools/life/music-practice-timer.html:285-293`（setInterval 递减与阶段切换）、`:271-278`（显示直接取 remaining）。
- 复现：设 5 分钟阶段 → 开始 → 切到其它标签 5 分钟再回来：实际剩余仍接近 `05:00`（仅少量回调），期望接近 `00:00` 或已完成（源码推演，未开浏览器）。
- 影响：`tools/life/music-practice-timer.html`；练琴时常把页面放后台听节拍/看谱，计时失真会让阶段时长与总练习量全部不准。

### LF-N42 新增阶段接受负时长，列表显示「-05:00」并在一秒内被跳过（低，确认缺陷）
- 描述：`addSegment` 用 `parseInt(prompt) || 5`，负数非 falsy 直接透传；负时长阶段在列表显示「-05:00」，开始后首次 tick 即因 `remaining <= 0` 被判为阶段结束，立刻跳段并播提示音。

### LF-N43 历史在加载预设/重置时就写记录，英文标签仍是中文（低，确认缺陷）
- 描述：`__tbn` 在每次 `loadTemplate` 后被调用并记录一次「练习计划总时长(秒)」，因此点预设、点重置都会写入历史，即使从未开始练习；历史标题「练习成绩历史（练习计划总时长(秒)）」把「成绩」与「计划时长」混为一谈。英文态 `LBL` 两个分支字符串完全相同，仍显示中文。

### LF-N44 倒计时到点判定挂在 rAF 上，标签页隐藏时不响铃且延迟触发（中，确认缺陷）
- 描述：到点判断只在 `tick()` 内做，而 tick 由 `requestAnimationFrame` 续排；标签页隐藏时 rAF 停止，`elapsed >= target` 永远不会被检查，`onFinish()`（提示音与完成态）要等用户切回标签才补触发。显示值本身用墙钟 `curElapsed()`，切回不会算错，但提醒会迟到。
- 证据：`tools/life/countdown-1.html:261-268`（`:265-266` 到点分支、`:268` rAF 续排）、`:263`（墙钟取值）。
- 复现：设 5 分钟 → 开始 → 切到其它标签 5 分钟：到点时无任何提示音/文案；切回后才弹完成态并响铃（期望按时提醒）。
- 影响：`tools/life/countdown-1.html`；倒计时的典型用法就是「开始后切走做别的事」，此时提醒失效，工具的核心价值丢失。
- 方案：到点提醒用独立 `setTimeout(target - elapsed)`（配合 Audio 解锁）触发，rAF 只负责渲染；并在 `visibilitychange`/`pagehide` 时用墙钟补判一次。

### LF-N45 目标为 0 秒时点开始立即「完成」并响铃，1e3 分钟被截成 1 分钟（低，确认缺陷）
- 描述：`applyTarget` 用 `parseInt` 只做 clamp 不写回：分钟 0/秒 0 → target=0，点开始后 tick 首次即 `0 >= 0` 判定完成，立刻响铃；`1e3` 被 parseInt 成 1 分钟；秒填 60 被 clamp 成 59 但输入框仍显示 60。0 秒目标还会随 `save()` 持久化，刷新后仍是完成态。
- 证据：`tools/life/countdown-1.html:232-239`（parseInt + clamp 无回写）、`:246-248`、`:265-266`、`:202-204`（load 时按 target 恢复完成态）。

- 影响：`tools/life/countdown-1.html`；空目标被当成一次「完成」并播放提示音，容易误判；数字输入被静默改写，界面值与实际目标不一致。
- 方案：`Number()` 解析 + 整数校验，最小值 1 秒；clamp 后把规范值写回输入框，避免显示值与 target 不一致。

### LF-N49 长度换算结果行前置数字与真实结果矛盾（高，确认缺陷）
- 描述：结果行先输出 `v / factors[k] * factors[from] / factors[from]`，该表达式化简后只剩 `v / factors[k]`，与后面的 `meters / factors[k]` 无关；只要源单位不是「米」，同一行就出现两个量纲不同的数字。

- 影响：`tools/life/length-converter.html`；4 个预设里 3 个非米输入，结果区首数字等于「输入值 ÷ 目标系数」（175 cm→mm 显示 175000），用户无法判断哪个才是结果，历史记录也只截取这段混杂文本。

- 复现：任意输入点「交换单位」→ 输入框、下拉、结果全部不变，仅页面滚动（期望与目标单位互换或至少提示不支持）。
- 影响：`tools/life/length-converter.html`；换算器最高频操作之一是反向换算，点击无反馈会被判为页面故障。
- 方案：增加「目标单位」下拉并真正交换 `fromUnit`/`toUnit`（数值取上次结果），或删除该按钮。

### LF-N51 精确年龄借位不足，显示负数天数（中，确认缺陷）
- 描述：`d < 0` 时只向上一月借一次天数，且借的是「上一自然月天数」；当出生日大于上月天数（29/30/31 日生日跨越 2 月或 4 月）时借完仍为负，且无后续修正。
- 证据：`tools/life/age-in-days.html:279-290`（y/m/d 分解）、`:301`（输出「精确年龄」）
- 复现：出生 2000-01-31，把系统日期设为 2026-03-01 → 实际 `26 岁 1 月 -2 天`（期望 `26 岁 1 月 1 天` 或 0 月 28 天口径）；出生 2001-01-31 同日同样得 `-2 天`。
- 影响：`tools/life/age-in-days.html`；每月头几天、生日为 29/30/31 的用户会看到负数天数，而「精确年龄」是本页主结果。
- 方案：借位后 `while(d < 0){ m--; d += new Date(nowY, nowM-1, 0).getDate(); }`，或改为「从出生日逐月推进直到不超过今天」的算法；补 31 日生日、闰年 2/29 用例。

### LF-N52 生日当天把「下一个生日」算成 365/366 天后（中，确认缺陷）
- 描述：`if(next < now)` 用含时分秒的 `now` 比较「今年生日 00:00」，生日当天该条件必然成立，直接跳到明年；再用 `Math.ceil` 取整得到 365（闰年后 366）。
- 证据：`tools/life/age-in-days.html:292-294`
- 复现：生日 11-04、当天 2026-11-04 10:00 → 实际「距离下一个生日：365 天」（期望「今天生日」或 0 天）。与 LF-N5（age-calculator 生日当天 `nextAge+1`）同源，但页面与文案不同。
- 影响：`tools/life/age-in-days.html`；生日当天正是查询高峰，结果与事实相反。
- 方案：与「今日 00:00」比较（`if(next <= todayMidnight) next.setFullYear(+1)`），相等时走「今天生日」分支；补当天/前一天/闰日用例。

### LF-N53 月度「工作日」重复扣减周末假期且忽略调休（中，确认缺陷）

### LF-N62 整段为零的分组不补「零」，页面自带示例 100200300 即输出错误（高，确认缺陷）
- 描述：`convertInt` 按四位分组后，只有 `convertGroup` 返回非空才拼接该段与 `万/亿/万亿`；全零段返回空串时既不追加单位也不补「零」，导致非零段之间的零被整段吞掉。页面「转换示例」自己列出的 100200300 期望正是「一亿零二十万零三百」，实现与之不符。
- 证据：`tools/life/number-to-chinese.html:423-429`（空段被跳过）、`:236`（示例期望「一亿零二十万零三百」）、`:500`（示例按钮含 `100200300`）
- 复现：输入 100200300 → 实际「一亿二十万三百」（期望「一亿零二十万零三百」）；100000001 → 实际「一亿一」（期望「一亿零一」）；100010001 → 实际「一亿一万一」（期望「一亿零一万零一」）；1000001 → 实际「一百万一」（期望「一百万零一」）。
- 影响：`tools/life/number-to-chinese.html`；核心转换在含整段零的金额/编号上缺字，且页面示例按钮会直接产出错误结果，用户会认为工具不可信。
- 方案：遍历时记录「前面是否已有输出」，遇全零段且后面仍有非零段时追加 `digits[0]`；仅忽略最高位的前导空段。补 100000001、100010001、100200300、1000001 用例。

### LF-N63 二进制/十六进制用 `>>>0` 截成 32 位，超 2³² 与负数整体回绕（中，确认缺陷）
- 描述：进制结果用 `(num >>> 0).toString(...)`，`>>>0` 会把数字强制转换为 32 位无符号整数；但入口条件只限制 `Math.abs(num) < 1e15`，因此 4,294,967,296 以上及负数都静默回绕，不报错。
- 证据：`tools/life/number-to-chinese.html:397-400`（`:399-400` 的 `>>> 0`）、`:350`（输入正则不限制位数）、`:398`（仅限制 1e15）
- 复现：4294967296 → 实际二进制「0」、十六进制「0x0」（期望「1 0000 0000 0000 0000 0000 0000 0000 0000」/「0x100000000」）；123456789012 → 实际 `0xBE991A14`（期望 `0x1CBE991A14`）；-5 → 实际 `0xFFFFFFFB`（期望「-0x5」或提示不支持负数）。
- 影响：`tools/life/number-to-chinese.html`；大额编号/金额转二进制时结果完全错误且无任何提示，负数则显示成 32 个 1。
- 方案：改用 `BigInt(intPart)` 或 `Number.prototype.toString` 并按输入字符串处理；若仅支持 32 位，则先校验 `0 <= num <= 4294967295` 并明确报错，负数加负号或拒绝。

### LF-N67 回款率只写 `max=100` 不校验，150% 时出现「未回款 -92500 元」（中，确认缺陷）
- 描述：`recv` 输入框仅靠 HTML `max="100"`，JS 计算不做范围校验；`inflow = rev * recv / 100`、`arrear = rev - inflow` 直接使用越界值。手输 150 或负数都照常出报表，现金流入甚至会超过营业收入。

- 复算：1 km →「1.000000e+6 毫米」「100000 厘米」；42.195 km → 毫米「4.219500e+7」；默认 1 m→cm 时「100 厘米」出现两次。
- 影响：结果难以直接抄写；重复行让用户误以为存在两种结果。
- 方案：≥1e6 改用千分位十进制（或仅 ≥1e12 才科学计数法）；目标单位已在列表中时不再追加。

### LF-N144 「去重字符数 × log2(池)」对长随机口令系统性低估，等级偏低（低，确认源码缺陷）
- 描述：模型用去重字符数替代实际长度（重复字符「不增加信息量」），20 位随机小写通常只有 11–14 种字符，被算成 52–66 bits，而真实熵约 94 bits；另 `entropy` 封顶 100，使 ≥100 bits 口令的破解时间一律相同。
- 证据：`tools/life/detector-checker-strength.html:270-274`（`uniqueCount` 与乘法）、`:286`（封顶 100）、`:288-306`（等级阈值）、`:120`（公式框自述）、`:375`（生成器符号集实际 26 个，公式按 32 计）。
- 复算：`abacadaeafagahaiajak`（20 位、11 种、真实熵 94.0）→ 51.7 bits / 52 分「一般」；`abcdefghijklmnopqrst`（20 种）→ 94 分「极强」；封顶后强口令破解时间统一为约 4 万亿年。
- 影响：本来安全的随机口令被判「一般」并被建议「增加符号」，用户可能把强密码改弱；超强口令的破解时长失去区分度。
- 方案：改用「长度 × log2(池)」再按重复模式扣减，或同时展示「长度熵 / 字符集熵」；封顶后注明「≥100 bits」。

#### LF-N146（①高，确认源码缺陷）世界时钟 6 个非法 IANA 时区，选中后时钟永久空白

- 影响：在「添加城市」中选 迈阿密/西雅图/波士顿/多哈/里约/檀香山（America/Honolulu 那条），时钟卡永远空白；而 `getOffset()` 走静态 offset 兜底仍显示 `UTC−5` 等，用户更难判断是脚本坏了还是时区本身无效。

#### LF-N147（①高，确认源码缺陷）长度换算「目标单位」下拉是死控件
- 证据：`length-converter.html:181-192` 提供目标单位下拉并绑 `onchange="convert()"`；但 `convert()` `:328-344` 只读取 `fromUnit`，随后 `Object.keys(factors).forEach` 输出「除源单位外的全部 9 个单位」，全文无 `toUnit.value` 读取（仅 `swap()` `:346-364` 用它对调源/目标）。

- 影响：用户按「输入数值 + 源单位 + 目标单位」的常规换算器心智操作，得不到对应单值；看起来能用、实际不响应的假控件。
- 方案：结果区首行输出「1 米 = 0.001 千米」并把该行高亮；或删除目标下拉、只保留「全单位列表 + 交换」，避免误导。

#### LF-N148（①高，静态推断·未真机）温度换算每键入一位即重写输入框，多位数被吞
- 证据：五个输入框均绑 `oninput`（`:213`、`:218`、`:223`、`:228`、`:233`）；`updateAll(c)` `:428-441` 无条件执行 `celsius.value=c.toFixed(2)`、`fahrenheit.value=f.toFixed(2)`… 覆盖包括用户正在编辑的那个框；全文无 `activeElement`/`focus`/`blur` 守卫。
- 复现（按源码推断）：在摄氏框内逐位键入 `100`：键入 1 → 值被改写为 `1.00`；再键入 0 得 `1.000`，解析仍为 1 → 又被写回 `1.00`；最终停在 1°C 而非 100°C。带 2 位以上小数的输入同样被截。预设按钮（−20/0/25/37/100）不受影响，故缺陷易被掩盖。
- 影响：核心输入框基本不可用；因未做真机/无头浏览器验证，结论标为静态推断，收口前需真机复核。
- 方案：写入前判断 `document.activeElement.id`，跳过当前聚焦框；或改为 `change`/失焦时统一格式化，输入期间只更新其它框且不强制 `toFixed`。

#### LF-N149（①中，确认源码缺陷）日期差「排除周末（只算工作日）」不改变主结果

#### LF-N152（③安全）全站注入无 SRI 的第三方远程脚本 bytegoofy
- 证据：每页 head 内有 `<!-- TOOLBOX-TTZZ -->` 块，例 `length-converter.html:107-117`：动态 `createElement('script')` 并把 `el.src` 指向 `https://lf1-cdn-tos.bytegoofy.com/goofy/ttzz/push.js?...`，插到首个 script 前；无 `integrity`、无 `crossorigin`、无失败回调。`tools/life/` 下 71 个页面均含该块（6 个抽样页全部命中）。
- 风险：无完整性校验的第三方脚本在页面上下文拥有完整 DOM/localStorage 权限，可读取本工具写入的历史记录并向第三方发起请求；与页面 FAQ「数据不会上传到任何服务器」的承诺存在口径冲突（即使脚本当前仅做推送，也无法从仓库侧证明）。
