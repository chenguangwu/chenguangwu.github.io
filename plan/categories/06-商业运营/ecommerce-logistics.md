## 2026-11-03 续查（并行批 F）

本批覆盖 8 页：`tools/ecommerce/calc-commission-2.html`、`tools/ecommerce/discount.html`、`tools/logistics/express-freight-calc.html`、`tools/logistics/load-calculator.html`、`tools/logistics2/loading-utilization.html`、`tools/logistics2/inventory-aging.html`、`tools/express/insurance-fee.html`、`tools/shipping/calc-76.html`。下列结论均来自源码阅读 + node 内存复算（复刻页内公式），未在浏览器执行。

### 06-F1 折扣率越界导致负实付与优惠倒挂（高，确认）
- 描述：`discount.html` 的 `calc()` 只校验 `isFinite`，未限制折扣率区间；折扣率 >100% 时实付为负，<0 时"优惠金额"为负、等效折数超过 10 折。
- 证据：`tools/ecommerce/discount.html:130-132,552-569`。复现输入 标价 880、折扣率 150 → 实际输出 实付 -440.00、优惠 1320.00、等效折数 -5.0 折；输入 标价 880、折扣率 -20 → 实付 1056.00、优惠 -176.00、折数 12.0 折。
- 影响：结果框可直接复制负数价格与倒挂优惠，用于活动定价或对账会算错。
- 方案：在业务 `calc()` 入口校验 `0 <= B <= 100`，越界时标红并停止输出；`input max=100` 只能挡步进器，不能替代 JS 校验。

### 06-F2 促销页宣称满减/优惠券叠加，实际只有单一折扣率（中，确认）
- 描述：标题、简介、功能特点、公式框与深度解析均写"满减门槛、优惠券面额、券叠加顺序"，但页面只有标价与折扣率两个输入，业务函数仅 `A*(1-B/100)`。
- 证据：`tools/ecommerce/discount.html:11,126-133,559,715-723,764-773`；页面 `input` 仅 `v0`/`v1`，无满减门槛、券面额字段。
- 影响：用户按标题找"满减/优惠券"工具，得到纯折扣计算，属内容名不符实（文件名与 URL 不可动）。
- 方案：在现有 URL 内补齐满减门槛、券面额、叠加顺序三项输入与分支（先满减后折扣、券互斥），或把文案收缩为"折扣计算"并明确不支持叠加，二选一。

### 06-F3 佣金页负费率产生负佣金并虚增到手（中，确认）
- 描述：`calc-commission-2.html` 业务函数对成交额与费率不做非负校验，负费率会把佣金算成负数并抬高到手金额。
- 证据：`tools/ecommerce/calc-commission-2.html:130-132,552-569`。复现输入 成交额 25000、费率 -5 → 实际输出 应付佣金 -1250.00、净到手 26250.00、每万元佣金 -500.00。
- 影响：与已记录的"负成本虚增利润"同类，可得出高于成交额的到手金额。
- 方案：成交额、费率均要求 ≥0，费率上限建议 100；越界标红停止计算。

### 06-F4 佣金页公式框承诺「阶梯与封顶」，实现无对应逻辑（中，确认）
- 描述：公式说明称支持"阶梯与封顶、多档费率试算"，深度解析示例称"若封顶 30 则佣金取 30"，但页面无封顶/阶梯输入，佣金恒为 `A*B/100`。
- 证据：`tools/ecommerce/calc-commission-2.html:126-127,559-563,718`；`fee=A*B/100` 无封顶分支，输入框只有 `v0`/`v1`。
- 影响：用户按示例预期封顶，实际不封顶，多档费率也无法试算。
- 方案：增加封顶金额与阶梯档位输入；若不做，删去阶梯/封顶描述与示例，避免误导。

### 06-F5 装载利用率：箱体大于车厢时 null 解引用抛异常（高，确认）
- 描述：三个朝向的 `fit` 全为 0 时 `bestFit` 仍为 0、`bestOrient` 保持 `null`，随后渲染直接读 `bestOrient.nx`。
- 证据：`tools/logistics2/loading-utilization.html:291-303,347-350`。复现输入 车厢 6.8×2.3×2.4、货物 10×3×3 → 实际 `bestFit=0`、`bestOrient=null`，`bestOrient.nx` 抛 `TypeError: Cannot read properties of null (reading 'nx')`，`result` 停在 `display:none`。
- 影响：页面无提示、结果区空白，用户只看到控制台报错。
- 方案：`bestFit===0` 时提示"单件尺寸大于车厢，无法装载"并 return；渲染前做判空。

### 06-F6 装载利用率只枚举 3 种摆放，漏 3 种正交朝向（中，确认）
- 描述：方向枚举数组仅 `[长宽高]、[长高宽]、[宽高长]` 三种，缺少另外三种排列，最大可装件数会被低估。
- 证据：`tools/logistics2/loading-utilization.html:291-303`。复现输入 车厢 5×3×2、货物 1.5×1.2×2 → 代码枚举得 6 件；六向全排列含 `[1.2,1.5,2]` 得 8 件。
- 影响：最大件数与"体积受限/重量受限"判定偏保守甚至错误。
- 方案：改为 6 种排列取最大，并记录最优方向用于展示。

### 06-F7 装载计算器默认车辆与载重上限不一致（中，确认）
- 描述：`cur` 初值为 `mid`（中型货车 5t），但 `maxLoad` 的 HTML 默认值是 1.5，首屏不会回填车辆参数。
- 证据：`tools/logistics/load-calculator.html:186,337-344`。复现默认参数（4.2×1.8×1.8、maxLoad 1.5、60×40×40、15kg）→ 重量上限 100 箱、限制因素"重量"、体积利用率 70.5%、重量 100%；把 maxLoad 改为 5 → 105 箱、限制因素"体积"、体积 74.1%、重量 31.5%。
- 影响：首屏把选中的 5t 车按 1.5t 计算，报告与车辆名矛盾。
- 方案：首屏按 `VEHICLES[cur]` 回填 L/W/H/maxLoad，或直接把 `maxLoad` 默认值改为 5。

### 06-F8 装载计算器单箱尺寸含非数字 → 静默 NaN 报告（中，确认）
- 描述：`split(...).map(parseFloat)` 后只判断 `p<=0`，`NaN <= 0` 为 false，非法尺寸会一路算成 NaN。
- 证据：`tools/logistics/load-calculator.html:359-360`。复现输入 `60×40×abc` → `parts=[60,40,NaN]`、`some(p=>p<=0)=false` → 可装箱数 `NaN`、利用率 `NaN%`，仅被末行 `replace(/NaN/g,'—')` 显示成"—"。
- 影响：不报错、不提示，报告全是破折号，用户不知输入有误。
- 方案：解析后逐项 `Number.isFinite` 校验，非法时 toast 并 return。

### 06-F9 装载计算器体积利用率被 0.75 损耗系数封顶（中，确认）
- 描述：`realVolBoxes=floor(volBoxes*0.75)`，随后 `volUtil=usedVol/vol*100`，体积利用率数学上不可能超过 75%，但页面仍按 70% 阈值输出"利用率偏低/良好"。
- 证据：`tools/logistics/load-calculator.html:368-370,377,417`。复现默认参数 → 体积利用率 70.5%、重量 100%，判"重量受限"；理论上限恒为 75%。
- 影响："装载率良好"与真实车厢填充率脱节，75% 以上永远报不出。
- 方案：把 25% 空间损耗改为可选输入并单独展示，利用率按实际占用体积计算；或在文案明确"已扣除 25% 空间损耗"。

### 06-F10 库存呆滞：周期 ≤0 静默替换/负周期令全部 SKU 判呆滞（中，确认）
- 描述：周期与阈值均用 `parseFloat(...) || 默认值`，0 会被静默替换；负周期使 `dailyOut<0`，周转天数走 `Infinity` 分支，全部判呆滞。
- 证据：`tools/logistics2/inventory-aging.html:135,139,280-281,291-293`。复现 周期填 0 → 实际按 90 天；周期 -30、库存 100、出库 300 → `dailyOut=-10`、`turnoverDays=Infinity`、`isSlow=true`；阈值填 0 → 实际按 180。
- 影响：用户以为按自填周期分析，结论可能完全相反。
- 方案：周期、阈值要求 >0，0/负数/空值标红并停止，不做静默兜底。

### 06-F11 快递运费负重量/负费用被接受（低，确认）
- 描述：五个输入均 `parseFloat(...) || 0` 且无区间校验，负数直接参与计费。
- 证据：`tools/logistics/express-freight-calc.html:124-142,246-256`。复现 首重1、首重费8、续重4、实重 -3、体积重 -2 → 实际输出 计费重量 -2.00 kg、预计运费 8.00 元，无任何提示。
- 影响：负数运单/异常录入会得到无意义报价且不报警。
- 方案：重量与费用要求 ≥0，计费重量 ≤0 时提示并停止。

### 06-F12 快递运费公式承诺抛重比与附加费，实现未输出（中，确认）
- 描述：公式框写"抛重比 = 体积重量 ÷ 实际重量"及"总费用另加保价费与偏远地区附加费"，但 `calc()` 只输出计费重量、超首重、运费，无抛重比、无保价/偏远输入。
- 证据：`tools/logistics/express-freight-calc.html:119,253-260`。
- 影响：用户按说明找附加费项找不到，也无法判断体积重与实际重的差距。
- 方案：输出抛重比卡片；补保价费、偏远附加费两个可选输入并计入总额。

### 06-F13 保价费：声明价值 0 仍收最低保费且净值为负；相关工具跨行业（低，确认）
- 描述：`val=0` 通过 `val<0` 校验，`fee` 取 `max(0,min)=1`，"保价后净值"变成 -1；同时相关工具 5 个全部指向 `../it/` 开发类页面。
- 证据：`tools/express/insurance-fee.html:149,255-270,315-334`。复现 声明价值 0、顺丰 → 应收保价费 1.00、最高理赔 0.00、净值 -1.00；相关工具为 .gitignore 生成器、properties 解析器、API 签名等。
- 影响：无意义输入仍出费用；相关推荐与快递保价主题无关，削弱站内串联。
- 方案：声明价值要求 >0；相关工具换成运费、材积、时效等物流同类页。

### 06-F14 船舶排水：`MTC×100/L` 实为「改变 1 m 纵倾」口径，却标注 1 cm（中，确认）
- 描述：`w=MTC*100/L` 求的是改变 100 cm（1 m）纵倾所需移动重量，但表格标签写"改变 1cm 纵倾需首尾移动重量"；按 1 cm 应为 `MTC/L`。
- 证据：`tools/shipping/calc-76.html:125,241`。复现默认参数 L180、B28、吃水 9.5/9.7/9.9、Cb0.72、ρ1.025 → 排水量 36079 t、MTC 512.60 t·m/cm；代码输出 284.78 t，按 1 cm 应为 2.85 t，相差 100 倍。
- 影响：配载人员若按该行数值移动压载，会严重误判。
- 方案：改为 `MTC/L` 并保留"改变 1cm"标签；或保留数值把标签改成"改变 1 m 纵倾"。

### 06-F15 船舶排水：中拱/中垂判据疑似反向（中，待验证）
- 描述：`deflection=Tm-(Tf+Ta)/2`，`>0.01` 判"中拱 (hog)"。中吃水高于首尾均值意味着船体中部下沉，按造船惯例应为中垂（sagging），需按教材/船级社口径复核后确认。
- 证据：`tools/shipping/calc-76.html:222,239`。复现 首吃水 9.5、中吃水 9.8、尾吃水 9.5 → `deflection=0.30 m`，页面判"中拱 (hog)"。
- 影响：变形方向提示与实际相反。
- 方案：核对口径后互换标签，或同时输出"中吃水相对首尾均值 +0.30 m"避免歧义。

### 留存优化
- 两页首屏 `calc()` 各被调用两次（通用脚本末尾 + 业务脚本末尾），`saveHistory()` 因此各写两条同值记录；建议只保留业务脚本的单次初始化，避免"最近计算"首屏重复。
- `restoreHistory(a,b)` 把数值拼进内联 `onclick`，遇 `Infinity`/特殊值会破坏内联 JS；建议改 `addEventListener` 或 JSON 序列化。
- 装载类两页可增加"多箱型/多包裹合计"入口，与本文档既有"体积重页缺多包裹合计"诉求合并实现。
- 运价页可加静态多快递公司价目对比表（纯前端静态数据），呼应既有"缺多快递公司价格对比"。
- 保价费页可补"保价 vs 不保价赔付差"对比卡，强化决策价值。
- 船舶页 `Cw` 输入 >1 时未校验，会直接放大 `Aw` 与 `TPC`；建议与 Cb 一样做区间校验并提示。
