### 单位价格相等仍判 B 更划算（中，确认缺陷）
- 问题：同类商品单位价格相等时给出 B 更划算，并称另一款约贵 1 倍，比较结论错误。
- 证据：`tools/biz/unit-price-compare.html:286-303` 中 `pa<pb?'A':'B'` 没有相等分支，且 `max/min` 直接用于「贵 N 倍」。例如 A 500g 10元、B 1kg 20元，均为 0.02 元/g，仍显示 B 更划算。浏览器行为未实测。
- 影响：`tools/biz/unit-price-compare.html`；此前 Z1 的固液量纲修复不等于此等价问题已修。
- 方案：按精度合理比较并显示等价；明确「价格为 X 倍」与「贵 X%」语义，测试零价格和近似相等的情况。

### BS-N1 单用户法估值少算 10⁴ 倍，把综合估值下限压到 0.2 万元（高，确认）
- 描述：交易对标法「单用户价值」把「月活(万) × 单用户价值(元)」又除以 10000，量纲多除一次；公式框与深度解析算例沿用同一错误。
- 证据：`tools/startup/valuation-calculator.html:523-525` 为 `uvValLo = mau * uvLo / 10000`；同页 `:156` 公式框写「月活(万) × 单用户价值(元) ÷ 10000（万元）」，`:349` 算例称「月活 300 万 × 30~80 元 → 0.9~2.4 万」。node 内存复算：`mau=10`、`uv=200` → 输出 0.2 万元；按「万 × 元 = 万元」正确口径应为 10×200 = 2000 万元。300 万 × 30~80 元正确为 9000~24000 万元，页面写 0.9~2.4 万。
- 影响：`tools/startup/valuation-calculator.html`；该法结果被低估 10000 倍，并成为综合汇总的最低值（见 BS-N2），用户会误判单用户变现价值极低或以为对标法失效。
- 方案：去掉 `/10000`（或改为「用户数(个) × 单价 ÷ 10000」并在标签写明单位）；同步修公式框、算例与 i18n 文案；汇总前做量纲一致性校验（某法结果与 PS 法相差 >100 倍时提示复核）。

### BS-N2 综合汇总把对标法上下限当两种方法各投一票（中，确认）
- 描述：`updateSummary()` 把「对标法(低)」「对标法(高)」分别推入结果数组，最低/最高/平均由单一方法的区间端点主导。
- 证据：`tools/startup/valuation-calculator.html:545-548`、`:553-556`。默认输入内存复算：Berkus 950 万、记分卡 2110 万、对标 0.2/5000 万 → 平均 2015.05 万、区间 0.2–5000 万；若每法只取一个代表值（对标取中位 1875.18 万）则为 1645.06 万。
- 影响：同页「建议以平均估值谈判」的 2015.05 万并非任何方法均值，叠加 BS-N1 的量纲错误后偏差更大。
- 方案：每法只投一票（对标法取区间中值），上下限单独展示；汇总中标注参与方法数与是否含区间法。

### BS-N3 DCF 输入名「首年自由现金流」与实现相差一年（中，确认）
- 描述：代码把该输入当作基期（上年）现金流，第 1 年先乘 `(1+g)`，与标签「首年」矛盾。
- 证据：`tools/startup/valuation-calculator.html:249` 标签，`:492-493` `cf = cf * (1 + g)` 起算。复算：`dcf_cf0=100`、`g=30%` → 第 1 年现金流 130 万而非 100 万；`:156` 公式框亦写「第 t 年现金流 = 上年 × (1 + 增长率)」。
- 影响：用户按「首年」理解填数会系统性高估估值（g>0 时），早期高增长场景偏差显著。
- 方案：标签改为「基期（上年）自由现金流」，或改为第 1 年直接取输入值、从第 2 年再增长；同步改公式框与算例。

### BS-N4 跑道不足 1 个月时「资金耗尽日期」显示为当天（中，确认）
- 描述：`Math.floor(runway)` 对小于 1 个月跑道取 0，耗尽日期等于当前日期；另 `setMonth` 遇月末会溢出到下月 3 日。
- 证据：`tools/startup/burn-rate.html:322-325`。复算：现金 10 万、月净消耗 17.5 万 → runway 0.5714 → floor 0 → 耗尽日期 2026/11/3（当天）。另测 `new Date(2026,0,31)` 加 1 个月 → 2026/3/3。
- 影响：高危场景给出「今天就耗尽」的失真日期，月末耗尽日记成次月 3 日，融资倒排时间表被误导。
- 方案：不足 1 个月改为按天显示（如「约 17 天后」）或按天迭代；加月时把目标日 clamp 到当月最后一天。

### BS-N7 保安质检：比率类输入未钳制，总分可破 100 且进度条溢出（中，确认）

### BS-N11 CSAT：阈值越界与众数并列取最低分（中，确认）
- 描述：阈值 `parseInt(...)||4` 既把 0 静默改成 4，又不钳制 1–5；众数用 `indexOf(max)`，并列时固定返回最低分。
- 证据：`tools/biz/summary-rater-csat.html:197-203`；阈值输入 `:124`（`min/max` 仅为浏览器软约束）。复算：评分 `5,4,5,3,4,5,2,4,5,3`、阈值填 9 → CSAT 0.0%；评分 `1,1,5,5` → 众数 1（1 分与 5 分各 2 次）。

### BS-N13 战略框架九宫格整表转置，高亮落在错误象限（高，确认）
- 描述：`matrix` 按「吸引力行 × 竞争力列」声明，但三行数组让首段（吸引力）随列变化，渲染又只截取 `split('-')[1]`（竞争力），造成行内容错位、★ 高亮跑到错误行。
- 证据：`tools/biz/analysis-47.html:223-229`（矩阵与渲染）、`:228`（表头「吸引力＼竞争力」）、`:220-222`（等级与行动映射）。
- 复现：默认输入（吸引力 7/8/6/5、竞争力 6/7/6/5）→ 定位「中-中」；矩阵标「中」行显示 中/中/中、标「低」行显示 强/强/强。设吸引力 10/10/10/0、竞争力 10/10/10/10 → 定位「高-强」，但 ★ 落在标「低」行第 3 列（`matrix[0][2]`）；期望 ★ 在标「高」行第 1 列。
- 影响：九宫格是核心交付物，用户按图会读成「低吸引力-强竞争力」，与文字行动建议相反。
- 方案：矩阵改为 `matrix = [[r+'-强', r+'-中', r+'-弱'] for r in ['低','中','高']]`；单元格直接渲染完整 `cell`（不要只取第二段），或为每格标注完整象限名；补四角与中心断言。

### BS-N14 行业吸引力满分 41 却按 40 归一，可输出 102.5%（中，确认）
- 描述：反向竞争项取 `11 - comp`，comp 最小 0 时贡献 11，使四维满分变为 41；公式框却写「÷40」，百分比可越 100%，且 8 个输入均未钳制 0–10。
- 证据：`tools/biz/analysis-47.html:217`、`:119`、`:126-136`。
- 复现：市场增速/规模/利润率各 10、竞争强度 0 → 行业吸引力显示 102（`102.5%`），期望 ≤100%；竞争强度填 20 → 反向项 -9，吸引力可为负百分比。
- 影响：核心评分越界，公式框与实现不符；负值/超限输入不报错。
- 方案：反向项改 `(10 - comp)` 使满分仍为 40，或分母改 41；对 8 个输入 clamp 0–10 并提示。

### BS-N15 财务分析页「期间费用」输入被读入后从未参与任何计算（中，确认）
- 描述：`exp` 在 `calc()` 中赋值后没有任何指标或评级使用它，改动该输入输出逐字不变。
- 证据：`tools/biz/analysis-manager.html:127`（输入）、`:212`（读入）、`:214-220`（六项指标与评级）。
- 复现：默认参数下把期间费用 200 改为 0（其余不变）→ 毛利率 40.00%、净利率 12.00%、流动比率 2.50、速动 2.00、资产负债率 40.00%、ROA 8.00%、评级「稳健」全部与改前相同（node 复算一致）。
- 影响：用户以为费用变化会影响利润诊断，实际被忽略；手填净利润也可能与「收入-成本-费用」自相矛盾（费用 200 但净利仍 120）。
- 方案：用 `(rev-cost-exp)/rev` 输出营业利润率并纳入评级，或删掉该输入；若保留手填净利润，明确提示「净利润须自行扣除期间费用」。

### BS-N16 净利为负仍评「尚可」，零分母直接折 0 混同「无此项」（中，确认）
- 描述：评级第二分支只要求 `cur>=1.2 && dar<70`，不要求净利为正；分母为 0 时利润率/流动比率直接写成 0。
- 证据：`tools/biz/analysis-manager.html:214-220`。
- 复现：收入 1000/成本 600/费用 200/净利 -100 → 净利率 -10.00%、流动比率 2.50、资产负债率 40% → 评级「尚可（基本健康）」；期望「偏弱」。流动负债改 0 → 流动比率/速动比率 0.00、评级「偏弱」；期望「—/无流动负债」。收入改 0 → 毛利率/净利率 0.00%、评级仍「尚可」。
- 影响：亏损企业被判「基本健康」，零负债被判「流动性压力」，零收入显示 0% 利润率。
- 方案：评级显式加 `net>0`；分母为 0 输出「—/不适用」；rev=0 不渲染利润率并提示。

### BS-N17 客服统计：达标阈值留空被折成 0 秒，达标率直接 0%（中，确认）
- 描述：`parseFloat(...)||0` 把留空/非法阈值折成 0，`meet` 只统计 ≤0 的时长，达标条数归零且不提示必填。
- 证据：`tools/biz/stats-time-response.html:201`、`:206`。
- 复现：默认时长 20/45/75/30/120，清空阈值（或填负值）→ 达标 0 条、达标率 0.0%；期望提示「请填写阈值」或保留上次有效阈值，而不是 0%。
- 影响：SLA 复盘时一个空输入把达标率打成 0%，结论反向。
- 方案：区分空值与 0；空值时显示「—」并标红提示；阈值 clamp ≥0。

### BS-N18 客服统计：输入按「秒」，深度解析与 FAQ 按「分钟」，同批数字差 60 倍（中，确认）
- 描述：输入框和公式框按秒，深度解析场景/算例与 FAQ 却按分钟并建议「推荐分钟」；同一批数字在两种口径下含义相差 60 倍。
- 证据：`tools/biz/stats-time-response.html:124`（秒）、`:121`（公式未写单位）、`:172-177`（分钟算例）、`:181`（FAQ「推荐分钟」）。
- 复现：按深度解析示例贴入 20,45,75,30,120 → 页面输出「平均响应 58 秒」；若按示例本意是分钟，期望「58 分钟」或输入框应标分钟。
- 影响：用户按示例录入会把分钟当秒，响应水平与达标率偏差 60 倍。
- 方案：统一为分钟（改标签与公式框）或统一为秒（改深度解析/FAQ）；加单位下拉并在结果中回显单位。

### BS-N19 客服统计：简介承诺 P90、FCR、分组，实际均未实现（低，确认）
- 描述：简介列「均值/中位数/P90」「一次解决率（FCR）」「按团队/个人分组对比」，实际输出只有条数、均值、中位数、极值、阈值达标率。
- 证据：`tools/biz/stats-time-response.html:254-257` vs `:207-211`；FAQ `:180` 还称页面「不区分指标类型」，与简介自相矛盾。
- 复现：页面无解决状态字段、无分组字段；输入任意时长只能得到五类统计，找不到 P90/FCR/分组入口。
- 影响：功能预期落空，用户可能把「响应时长阈值达标率」误当解决率。
- 方案：补 P90、FCR（需新增「是否解决」字段）与分组维度；或把简介降为已实现口径。

### BS-N20 胜任力评估：留空按 0 分计入，11 分/负分照算不钳制（中，确认）
- 描述：六维用 `+value || 0`，留空按 0 分计入总分；同时未按 1–10 钳制，11 分或负分直接参与加权。
- 证据：`tools/biz/assessor-49.html:211`、`:214`、`:217`。
- 复现：默认（管理岗）综合 6.95；清空「专业知识」→ 5.90（期望提示必填或按其余维度均值，而非按 0 拉低 1.05）。六维全填 11（管理岗）→ 综合 11.00/10、仍判「卓越」；填 -1 → 负分并「不胜任」。
- 影响：漏填与越界都能得到看似正式的总分，人才盘点结论失真。
- 方案：区分空值与 0；按 `min/max` 钳制 1–10 并提示；总分再钳制 0–10，或超限时拒绝计算。

### BS-N21 胜任力页深度解析算例两个综合分与实际权重表算不出（低，确认）
- 描述：算例写技术岗约 8.05、管理岗约 7.60，按页面权重表复算分别应为 7.90 与 7.65。
- 证据：`tools/biz/assessor-49.html:185`；权重表 `:212`。
- 复现：六维 8/7/9/7/7/8，node 按 `:212` 权重复算 → 技术岗 7.90、管理岗 7.65；页面写 8.05 / 7.60。
- 影响：用户拿算例校验工具会对不上，误以为工具或权重有错。
- 方案：按实际权重重算改写算例；加断言「各岗位权重和为 1」且示例值可由页面函数复现。

### BS-N22 风险排查：删光风险点后仍显示「低风险-常规管理」（中，确认）
- 描述：风险点可被全部删除，`results` 为空时 `maxRisk=0`，总体等级落到 `else` 分支「低风险-常规管理」，页面仍显示「共识别 0 个风险点」。
- 证据：`tools/biz/assessor-risk-8.html:196-199`（删除无下限）、`:216`、`:218-221`。
- 复现：点 3 次 × 删光默认风险点 → 总体「低风险-常规管理」、风险点总数 0、高/中/低均 0；期望「未录入风险点，请先添加」。
- 影响：空表被当成「零风险」绿灯，评审时可能据此放行。
- 方案：`results.length===0` 时输出中性提示并禁用评级/参考标尺；`removeRisk` 保留至少 1 项，或允许清空但明确「未知」而非「低风险」。

### BS-N23 风险排查：参考标尺永不渲染，风险名未转义会截断输入（低，确认）
- 描述：① 标尺条件 `typeof value==='number'` 引用了不存在的变量（`value` 只在 map 回调内声明），`#resRefBar` 始终为空；② 风险名未经转义写入 `value` 属性与结果表，含 `"` 时重渲染会截断名称。
- 证据：`tools/biz/assessor-risk-8.html:258`（`typeof value`）、`:180`（`value="'+r.name+'"`）、`:233`（表格 `r.name`）。
- 复现：任意输入下 `#resRefBar` 始终为空；把风险名改为 `A"B` 后点「+ 添加风险点」→ 该输入框回显 `A`（其余被当属性丢弃），表格也可能被截断。
- 影响：标尺功能缺失；名称含英文引号或 `<` 时数据丢失/布局破坏。
- 方案：标尺改用 `maxRisk`；名称渲染前 `ToolBox.escHtml`，表格同样转义。

### BS-N24 干系人分析：增删干系人会静默丢弃已编辑内容（中，确认）
- 描述：`renderSh()` 只从 `shData` 重建，而名称输入与权力/利益下拉都没有把编辑写回 `shData`；点「+ 添加干系人」或「×」会用旧值重绘。
- 证据：`tools/project/analysis-28.html:212-223`（renderSh 读 shData）、`:216-218`（输入/下拉无回写）、`:225-226`。
- 复现：把「业主/投资方」权力 5 改为 1、名称改为「甲方」，不点「分析矩阵」，直接点「+ 添加干系人」→ 业主恢复权力 5 与原名称；期望保留编辑。
- 影响：增删行会丢失已录入的干系人信息，用户需重填。
- 方案：重绘前先 `syncShFromDom()` 从当前 DOM 回写 `shData`；或给输入/下拉加 `oninput/onchange` 即时更新。

### BS-N25 干系人分析：象限与「需重点应对」用两套阈值，重点管理可落选（低，确认）
- 描述：象限按权力/利益阈值（p≥3 且 i≥3 为「重点管理」），重点清单却用 `score>=10`；两者不同源。
- 证据：`tools/project/analysis-28.html:235-240`、`:245-246`。
- 复现：只保留一名干系人权力 3、利益 3 → 结果「重点管理」，但下方无「需重点应对」提示；权力 2、利益 5 → 结果「随时告知」，却被列入「需重点应对（关注度≥10）」。
- 影响：同一页面两套优先级口径，沟通资源可能投给错误对象。
- 方案：统一以象限为主，重点清单取「重点管理」象限；或把清单标题改为「关注度≥10（不等于重点管理）」并单列象限优先级。

### BS-N26 项目风险循环：参考标尺取第 5 项风险值而非最高值（中，确认）
- 描述：标尺读取 `score`，而 `score` 是 for 循环里的 `var`，循环结束后等于第 5 项风险值，不是上方展示的 `maxScore`。
- 证据：`tools/project/assessor-risk-9.html:213-215`（`var score=p*imp`）、`:221`（maxScore）、`:240`（refBar 用 `score`）。
- 复现：前 4 项设 5×5=25，第 5 项设 1×1=1 → 上方「最高风险值 25 / 25」「整体极高风险」，参考标尺却显示 1（低风险区）。
- 影响：同一结果卡内两个风险结论互相矛盾，读者可能按标尺的低风险色放松处置。
- 方案：标尺改用 `maxScore`；若需展示逐项分布，另设数组传参，不复用循环变量。

### BS-N27 项目风险循环：10–15 档在公式框叫「较高」、结果卡叫「高风险」（低，确认）
- 描述：公式框把 10–15 称「较高」、16–25 称「高风险」，结果卡却把 10–15 标「高风险」、16–25 标「极高风险」，同一档两种叫法。
- 证据：`tools/project/assessor-risk-9.html:125`（公式框）、`:219-220`（代码分级）。
- 复现：任一项 3×4=12 → 结果「高风险」；按公式框应称「较高」。5×5=25 → 结果「极高风险」；公式框称「高风险」。
- 影响：对照公式框复核时误判等级，10–15 档容易被当成最高档。
- 方案：统一四档命名（低/中/较高/高 或 低/中/高/极高），同步公式框、结果卡、图例与 CSV。

### BS-N28 HSE 检查：关键项 0 分仍可评「优秀」，缺一票否决（高，确认）
- 描述：10 项纯加总评分，没有「关键项一票否决」；页面自己称为「一票否决/重大隐患」的特种作业持证项即使 0 分，其余 9 项满分仍得 18 分判「优秀」。
- 证据：`tools/project/checker-training-hr-1.html:208`（纯 `total+=`）、`:211-214`（仅按总分分级）、`:157`、`:164`（一票否决/即时停工表述）。
- 复现：仅「特种作业持证」选不达标（0 分），其余 9 项均达标（2 分）→ 总分 18/20、达标率 90%、等级「优秀」，建议「安全管理体系健全」；期望触发「重大隐患/停工整改」而非优秀。
- 影响：HSE 自评可能把无证上岗等重大隐患判为优秀，直接违背页面 FAQ 与法规要求，安全风险高。
- 方案：为关键项（特种作业持证、重大隐患等）设否决位：任一为 0 时整体最高只能「不合格/限期整改」并置顶红色提示；或在总分旁单列「关键项」状态。
