📐 工作原理与说明
先对 .proto 源码做词法切分得到记号序列，再用递归下降解析：顶层依次识别 syntax、package、import、option、message、enum、service 声明。字段解析先连续读取 repeated / optional / required 修饰符，再读类型名（遇到点号时继续拼接成完整限定类型名），接着读字段名；遇到等号时把后面的记号取整作为字段编号；遇到方括号时逐项读取「键 = 值」对填入字段选项，逗号分隔，最后以分号结束。oneof 解析名称与花括号内若干「类型 名 = 编号」字段。message 解析时对花括号内记号分派：message 递归下探、enum 解析枚举、oneof 解析联合、reserved 读取分号前逗号分隔的编号列表、option 读取键值对，其余按普通字段处理。读取时若当前记号与期望记号不一致，抛出「期望某记号」的解析错误
解析 Protocol Buffers 的二进制编码结构。
  • 编码：每个字段为 key + value，key 是 varint，等于 (字段号 << 3) | wire_type。
  • wire type：0 为 varint、1 为 64 位、2 为长度前缀（字符串/嵌套/字节）、5 为 32 位。
  • varint：每字节低 7 位存数据，最高位为 1 表示还有后续字节，小端排列。
  • 局限：无 .proto 时只能还原字段号与原始值，字段名与类型需 schema 才能确定。

❓ 常见问题（FAQ）

无 schema 能解析吗？
不能，Protobuf 自描述弱，需 .proto。
为什么解析出来的字段对不上？
多半是 schema 版本不一致：Protobuf 靠字段编号（而非名称）识别字段，收发双方若用了不同版本的 .proto，同一个编号会被解释成完全不同的含义，且不会报错。因此必须保证解析用的 .proto 与发送方完全一致，并做好向后兼容（不复用已废弃的编号）。
