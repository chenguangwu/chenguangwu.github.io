📚 深度解析：推理吞吐估算

💡 常见使用场景

  • 吞吐≈生成 token 数 / 端到端时延(tokens/s)，衡量服务处理速度。
  • 受模型大小、批大小、KV 缓存与硬件带宽共同影响，非仅由 FLOPs 决定。
  • 容量规划用 吞吐×并发上限 估算峰值 QPS，需预留余量防雪崩。
单请求吞吐
生成 200 token 耗时 4s → 吞吐=50 tokens/s。若单卡支持 4 并发且各 50 tok/s，总吞吐≈200 tok/s；但实际共享 KV 缓存与带宽，并发增益低于线性。

❓ 常见问题（FAQ）

为什么吞吐不随并发线性增长？
显存带宽与算力是共享瓶颈，多请求竞争 KV 缓存与计算单元，边际吞吐递减；需实测找到拐点再定并发上限。
首 token 延迟和吞吐冲突吗？
常冲突。大模型首 token 受预填充耗时影响，吞吐受解码并行影响；优化方向相反时按业务(对话要低延迟、批处理要高吞吐)取舍。
