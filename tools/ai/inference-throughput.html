🔮 Inference Throughput Estimator

Estimate inference throughput in tokens per second from the generated token count and end-to-end latency, for capacity planning.

📐 计算公式 / 原理
推理总吞吐（本页代码口径）：单请求时延=TTFT+（生成 tokens−1）×TPOT；总吞吐=tokens×并发批量÷单请求时延（tokens/s）；单请求吞吐=tokens÷单请求时延。校验：空值按 0 兜底，TTFT 可为 0，TPOT 或并发为 0 时结果非有限并追加警示「部分结果无定义」。判据：无固定分级，总吞吐衡量服务整体利用率，结果保留 1 位小数、非有限时显示 —。
推理服务的核心指标：总吞吐衡量集群利用率，单请求吞吐才是用户感知的快慢。本页把端到端时延拆成「首 token 延迟 TTFT」与「每 token 间隔 TPOT」两段：TTFT 反映预填充与排队，TPOT 反映解码速度；总时延=TTFT+(tokens−1)×TPOT。实际 batching 会拉长 TTFT/TPOT 并受带宽瓶颈限制，请用实测两段时延复核，再按 SLO 取舍。

📐 计算公式与说明

单请求吞吐与时延（本页代码口径，与上方总吞吐互补）：单请求时延=TTFT+（生成 tokens−1）×TPOT；单请求吞吐=生成 tokens÷单请求时延（tokens/s）；平均每 token 毫秒=单请求时延×1000÷生成 tokens；纯解码速度≈1000÷TPOT（ms/token）。校验：与总吞吐共用同一组输入，TPOT 或并发为 0 时该项无定义并同样触发警示。判据：本页不建模 batching 对 TTFT/TPOT 的拉长；实际容量规划须用实测 TTFT、TPOT 与带宽拐点复核。

实际受批大小与排队影响。

📚 深度解析：推理吞吐估算

💡 常见使用场景

  • 吞吐≈生成 token 数 / 端到端时延(tokens/s)，衡量服务处理速度。
  • 受模型大小、批大小、KV 缓存与硬件带宽共同影响，非仅由 FLOPs 决定。
  • 容量规划用 吞吐×并发上限 估算峰值 QPS，需预留余量防雪崩。
单请求吞吐
生成 200 token 耗时 4s → 吞吐=50 tokens/s。若单卡支持 4 并发且各 50 tok/s，总吞吐≈200 tok/s；但实际共享 KV 缓存与带宽，并发增益低于线性。

❓ 常见问题（FAQ）

为什么吞吐不随并发线性增长？
显存带宽与算力是共享瓶颈，多请求竞争 KV 缓存与计算单元，边际吞吐递减；需实测找到拐点再定并发上限。
首 token 延迟和吞吐冲突吗？
常冲突。大模型首 token 受预填充耗时影响，吞吐受解码并行影响；优化方向相反时按业务(对话要低延迟、批处理要高吞吐)取舍。
